# Solution Design Requirements
# 企业级 LLM 自维护知识库系统

> **文档说明：** 本需求文档基于《企业级 LLM 自维护知识库方案研究报告》（Andrej Karpathy LLM Wiki 范式）提炼生成，作为系统建设的需求基线。

---

## 1. Business Problem（业务问题）

企业内部知识管理面临严峻挑战，传统解决方案（RAG 检索、Confluence、Notion 等）存在以下核心痛点：

- **重复查询无积累**：每次查询均从头检索，知识没有复利效应，相同问题反复消耗资源。
- **矛盾与不一致**：多份文档内容冲突时，RAG 每次可能给出不同答案，甚至自相矛盾，可信度低。
- **维护负担极重**：文档越积越多，交叉引用、更新摘要全靠人工，Confluence/Notion 沦为"知识坟场"，无人维护。
- **知识孤岛**：知识散落在代码仓库、Slack/飞书、邮件、Jira、设计文档等多套系统中，缺乏统一整合层。
- **人工成本倒挂**：知识增长的价值赶不上维护成本，人员疲于更新后选择放弃，知识资产持续流失。

**受影响群体**：研发团队、知识管理团队、新员工入职、客服支持、决策层及全体知识型员工。

---

## 2. Business Goal / Objective（业务目标）

构建企业级 **LLM 自维护知识库（LLM Self-Maintaining Wiki）系统**，实现以下目标：

- **知识自动积累**：LLM 代替人持续编写和维护结构化 Wiki 知识库，每次交互均可增益知识库，实现知识复利。
- **维护成本近零**：LLM 自动完成 90% 以上的知识整理更新，人工仅需战略性审查关键内容。
- **知识质量提升**：知识库始终保持最新、一致，LLM 自动消除陈旧/冲突内容，提高信息准确度。
- **全员提效**：员工搜索和整理信息时间大幅减少，新员工上手加速，全员生产力提升。
- **组织敏捷性**：知识沉淀在系统而非个人，随企业演进实时更新，组织对变化的响应更快。

**成功衡量标准**：

| 指标 | 目标值 |
|------|--------|
| 知识库自动更新率 | ≥ 90%（人工介入 < 10%） |
| 新员工知识获取时间 | 较基线缩短 ≥ 50% |
| 知识查询准确率 | ≥ 85%（人工抽查） |
| 知识内容冲突率 | < 5% |
| 月度 API 调用成本 | 控制在预算内（TBD） |

## 3. System Scope（系统范围）

**本次建设范围（In Scope）：**

- **LLM Wiki 核心引擎**：Ingest（知识摄入）、Query（智能查询）、Lint（健康检查）三大核心流程
- **三层架构建设**：
  - 原始素材层（Raw Sources）：多源数据接入与预处理 Pipeline
  - Wiki 知识库层：LLM 维护的结构化 Markdown 知识库
  - Schema/配置层：AGENTS.md 规则、目录结构、命名规范等治理配置
- **数据源接入**：对接企业现有知识系统（代码仓库、飞书/Slack、文档系统、邮件等）
- **混合检索层**：向量索引 + 知识图谱 + 结构化查询混合检索
- **质量门控机制**：自动校验、第二模型审查、人工审核工作流
- **多用户协作支持**：权限管控、审稿流程、审计日志
- **治理与安全**：数据分类、访问控制、版本审计、合规机制
- **管理界面**：Wiki 可视化浏览、知识健康仪表盘、审核操作台

**本次为绿地（Greenfield）建设**，在现有协作平台基础上新增 AI 知识管理层。

## 5. Current State（现状描述）

**现有知识管理体系**：

- **文档平台**：Confluence/Notion/飞书文档 — 内容更新频率低，大量页面过时，难以维护交叉引用
- **即时通讯**：Slack/飞书群组 — 知识分散于对话流，无法沉淀，信息难以检索
- **代码仓库**：GitHub/GitLab — 技术文档与代码脱节，README 普遍过时
- **问答系统**：部分团队使用 RAG 方案（向量数据库 + 检索生成），但面临以下问题：
  - 无状态，每次重新检索，无知识积累
  - 文档冲突时产生不一致回答
  - 随文档增多，噪声增加，回答质量下降
- **现状痛点**：人工整理成本高，知识利用率低，重要经验随人员流失而消失

## 6. Target State（目标架构）

### 整体架构模式

采用 **"人类策展 + LLM 维护"** 三层架构，实现 **人机协作知识管理**：

```
┌─────────────────────────────────────────────────────────┐
│                     用户 / Agent 接入层                   │
│        (问答界面 / API / Slack Bot / 飞书机器人)          │
└─────────────────────┬───────────────────────────────────┘
                       │ Query
┌─────────────────────▼───────────────────────────────────┐
│                   Wiki 知识库层（核心）                    │
│  结构化 Markdown 集合：主题页、实体词条、索引              │
│  LLM 全权创建维护 | 双向链接 | 版本管理 | 人工可审阅        │
│  存储：Git 仓库 / 企业协作平台                             │
├─────────────────────────────────────────────────────────┤
│  混合检索层：向量索引 + 知识图谱 + 结构化全文搜索           │
└──────┬──────────────────────────────────────────────────┘
       │ Ingest / Lint
┌──────▼──────────────────────────────────────────────────┐
│                   原始素材层（只读）                       │
│  代码仓库 | 飞书/Slack 会话 | 邮件 | Confluence          │
│  PDF/Word 文档 | Jira/项目管理 | 行业报告                  │
└─────────────────────────────────────────────────────────┘
       │
┌──────▼──────────────────────────────────────────────────┐
│              Schema / 配置层（人类定义）                   │
│  AGENTS.md：目录规范 | 命名规范 | 治理规则 | 工作流配置    │
└─────────────────────────────────────────────────────────┘
```

### 核心工作流

| 流程 | 描述 |
|------|------|
| **Ingest（摄入）** | 新文档进入时，LLM 通读全文，生成摘要页，更新相关知识页（10-15页/次），标记矛盾，记录更新日志 |
| **Query（查询）** | 用户提问 → LLM 搜索 Wiki → 综合作答 → 有价值答案回写 Wiki，知识持续生长 |
| **Lint（审查）** | 定期扫描知识库，发现冲突/过时/遗漏链接，触发更新或人工审核通知 |

### 多步处理 Pipeline

```
原始数据扫描 → 规则筛选（过滤无效文件）→ 格式转换（OCR/文本提取）
→ LLM 分类摘要 → 质量门控校验 → Wiki 组装写入 → 双向链接更新
```

- **云提供商**：TBD（优先企业现有云，如 Azure / 阿里云 / 腾讯云）

## 9. Assumptions（假设条件）

- LLM API 已获得企业合规许可（私有部署或已签署数据处理协议）
- 企业现有知识系统均有可用 API 或导出接口，可批量提取数据
- 知识库采用 Markdown 格式存储，版本管理基于 Git 或兼容平台
- 人类管理员负责定义和维护 Schema/AGENTS.md 配置文件
- 重要知识更新需经人工审核（Quality Gate），非完全自动化
- 初期以单一业务域（TBD，如研发文档 或 客服FAQ）作为试点，验证后推广
- 多数原始素材为中文内容，LLM 需支持中文处理
- 企业有意愿将部分知识维护工作交由 AI 自动处理

## 12. Known Risks（已知风险）

| 风险 | 影响 | 可能性 | 初步缓解措施 |
|------|------|--------|------------|
| **LLM 幻觉与错误**：LLM 可能归纳错误或臆造知识，错误链接无关信息 | 高 | 中 | 构建质量门控（Quality Gate）；重要内容人工复核；关键领域强制审核 |
| **知识失真**：LLM 摘要可能遗漏细节，导致信息损失 | 高 | 中 | 严格保留原文作审计回溯；定期对 Wiki 摘要质量抽查；LLM 回答时引用原始素材来源 |
| **数据安全与隐私泄露**：内部机密信息经 LLM API 处理存在泄露风险 | 高 | 低 | 优选私有部署模型；敏感数据访问限制；签署数据处理合规协议；数据脱敏处理 |
| **成本超支**：大规模文档处理涉及大量 LLM API 调用 | 中 | 中 | 优先规则和小模型处理简单任务；设置调用预算告警；Pipeline 批量处理降低成本 |
| **实现复杂度高**：多系统集成、容错 Pipeline、企业级治理工程量大 | 中 | 高 | 分阶段建设（MVP 先聚焦核心引擎）；借助开源方案（LLMWiki、Link 等）降低开发成本 |
| **知识治理不足**：缺乏内容所有者责任制，导致知识库逐渐失控 | 中 | 中 | Pipeline 集成分类体系与评分；设定内容所有者；定期 Lint 审查 + 通知机制 |
| **多用户协作冲突**：并发写入导致 Wiki 内容不一致 | 中 | 低 | LLM 提交更新前设审批机制；基于 Git 的版本管理；写操作加锁机制 |
| **数据源接入阻力**：部分系统无开放 API 或数据导出受限 | 低 | 中 | 提前评估各系统接入可行性；优先接入有 API 的系统；复杂系统采用人工导出 + 批量上传方式 |

### 核心设计原则（来自研究报告）

1. **人类策展 + LLM 维护**：人类决定放入什么知识、定义组织规则；LLM 负责知识枢纽维护
2. **知识随使用而生长**：每次有价值的问答结果回写 Wiki，知识持续积累
3. **规则优先 + 小模型处理**：简单分类、格式转换优先用规则/小模型；复杂推理才调用大模型
4. **断点续跑 + 幂等设计**：Pipeline 支持失败重启，重复运行不重复写入
5. **质量门控**：引入第二模型或人工审核，不达标内容不入库
